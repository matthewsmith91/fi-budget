# AGENTS.md

## What is this

A shared household budgeting app for two users (Matt and Jessica) that replaces the YNAB + Empower split. It combines envelope budgeting with real sinking funds, an emergency fund tracked as an allocation of an account (not the whole account), percentage-based income rules (e.g. tithe 10% before anything else), investment goals inside shared brokerage accounts, and retirement / 529 / net-worth planning. It is local-first: every device holds the whole budget in SQLite and works alone; an optional sync server (Phase 2) keeps both users' devices in step.

The app tracks and plans; it never moves money. One household, two users, no public sign-up.

The full spec and phased roadmap live in `docs/specs/Household Budget App — Spec & Plan.md`. Phase 0 (foundations), Phase 1 (budget core) and Phase 2 (sync and import) are built. The spec is authoritative where this file disagrees.

## Project Layout

npm workspaces monorepo orchestrated by Turborepo: `apps/web` (React 19 + Vite PWA), `apps/api` (Express 5 + `node:sqlite` server), `packages/core` (pure TS domain layer, no DOM), `packages/ui` (shared components, currently empty).

- `apps/web/src/client.ts` is the only handle on the domain layer. Views read with `useBudgetQuery` and call `refresh()` (`data.ts`) after any write.
- `apps/web/src/worker/budget.worker.ts` opens SQLite in OPFS, runs migrations and serves the RPC API. `apps/web/e2e` holds Playwright tests that run against the production build in real Chrome.
- `apps/web/src/sync-state.ts` holds the pure logic behind `SyncBanner`. The settings sidebar swaps in on `#/settings`, with pages `household`, `connections`, `payee-rules`, `income-rules`, `imports`, `backups`.

**Where code goes:** domain logic (anything that touches money or the budget file) goes in `packages/core` so it runs unchanged in the browser worker, in Node tests, and later on the sync server and in Capacitor. The UI never touches SQLite: it calls the `BudgetApi` interface in `packages/core/src/api.ts` through `apps/web/src/client.ts`, and every call is a message to the worker. To add a capability, extend `BudgetApi`, implement it in `createBudgetApi`, and test it against an in-memory database (`openMemoryAdapter` in `test-utils.ts`).

**Shared component library:** reusable UI components belong in `packages/` (starting with `packages/ui`), not inside an app. The web interface and the planned mobile apps both consume it, so components there should avoid web-only assumptions where practical. Apps import it as `@budget-fi/ui`.

## Commands

Commands are the scripts in the root `package.json` (npm 11 + Turborepo). `npm run test:e2e` needs Google Chrome installed. `npm run format:check` is what CI runs. `npm run build -w web` is `tsc -b && vite build` and also generates the service worker. In `apps/web`, `npx pwa-assets-generator` regenerates icons from `public/icon.svg`.

Self-hosting, deployment and server configuration (Docker/Caddy, `ORIGIN`/passkeys, `BANK_KEY`, the daily bank pull): see the `self-hosting` skill.

The service worker only exists in production builds, so test PWA behavior with `npm run test:e2e` or `npm run build -w web && npx vite preview`.

## Architecture

**Core design rule:** where money sits (accounts) is separate from what money is for (envelopes/categories/goals). Every balance is derived from an append-only ledger (`allocations`, `transactions`, `unit_events`); nothing stores a running balance. Edits add rows instead of overwriting, which also makes concurrent edits by two people safe.

**Key invariants**

- Category balance = its own allocations + the sum of its goals' balances − spending.
- Envelopes held in an account can never add up to more than that account's balance.
- Spending from a goal is a planned draw-down, never flagged as overspending.
- Goals (`goals.ts`, synced table `goals`): a goal belongs to one category (never a card payment category). Money reaches it through allocations with `goal_id` and leaves through splits with `goal_id`, so a category's assigned, activity and available already include its goals; `rollCategories` is unchanged. A goal's balance accumulates across months (no rollover rule) and is computed in `goalFigures`. A split's goal must belong to its category, and changing the category drops the goal. `allocate` and `moveAllocation` take goal ids, which is how money moves between a goal and its category's unassigned part. Archiving moves what the goal holds (or owes) back to the category in the given month, keeps history, and rejects new money or spending (an old transaction that already uses it stays editable). Delete is only for a goal with no history. Monthly needed is `ceil((target - opening balance) / months)` counting the current and target months, null without a date; percent funded rounds down and is capped at 0-100 (`goalProgress`). A goal may be "held in" an open budget account that isn't a credit card (`goals.held_in_account_id`, migration 12). Nothing enforces it: `getAccountHoldings(month)` compares the goals held in an account (only goals with a positive balance) with the account's balance through that month, and the budget shows a warning when they exceed it. Deleting the account clears the link.
- Need/want (`categories.need_or_want`, default want; `transaction_splits.need_or_want_override`, null follows the category): a split's tag is its override, else its category's. Changing a single-line transaction's category drops the override, like the goal. `getNeedsWantsReport` (`reports.ts`) sums categorized spending from on-budget accounts by effective tag per month (refunds net off, goal draw-downs and categorized transfers to tracking accounts count, uncategorized spending does not) and averages the trailing 3, 6 and 12 months ending at the chosen month. A window longer than the spending history averages over the months since the first spending, not over empty months. The Reports page opens on the last complete month.
- Emergency fund (`emergency-fund.ts`): the household row (`households.emergency_fund_category_id`, `_months` default 6, `_window` default 12; migrations 13-14, synced with the household) names one ordinary category as the emergency fund, so it appears in the budget like any other and money is assigned, moved and spent through the normal category flows. `getEmergencyFund({ month, asOf })` returns target = months × the average Need month over the trailing `window` (3-12) months ending at `month` (via `averageNeedsWants`, so a short history averages over the months it has), the category's available at the end of `asOf` (rollover and its goals included, from `monthBalances`), the shortfall, and months covered (balance ÷ average Need, rounded down to a tenth, null with no Need spending). The Reports page averages through its chosen month but takes the balance as of today. A card payment category can't be the fund; deleting the category clears the setting. The held-in account over-allocation warning is goal-only, so it doesn't cover the fund.
- Income rules (`income-rules.ts`, synced table `income_rules`; migration 15): income is an approved, uncategorized inflow in an on-budget account that isn't a transfer or a reconciliation adjustment. A rule matches by payee words and/or account (at least one), takes a percent (up to three decimals, of the deposit or of the `transactions.gross_amount` typed on it) or a fixed amount, and names a category or goal. Every matching rule runs, lowest `priority` first, and none gives more than is left of the deposit; the remainder stays in Ready to Assign. A gross-basis percent gives nothing until the gross amount is typed. `settleIncome` is the single place rule allocations are made: it compares what the rules want for a deposit with the `source = 'rule'` allocations that carry its `source_transaction_id`/`income_rule_id` and appends the difference (the ledger is append-only, so a reversal is a negative entry). Ids are `rule:<txn>:<rule>:<month>:<n>`, so two devices settling the same state write the same rows. It runs on create, on edits that touch date, payee, amount, category, gross or reversal link, on delete and on inbox approval, never on imports (unapproved) or the YNAB import. A reversal is an outflow with `transactions.reverses_id` set to the deposit (typed on the register as "Takes back"); the deposit's shares shrink in proportion (gross too) and the take-back is booked in the reversal's month, so a budgeted month isn't rewritten. Rules are not retroactive: creating, editing or deleting one leaves past allocations, and a rule that was deleted or can't run (hidden category, archived goal) is left alone while its deposit stands. `applyIncomeRules(month)` settles a month on request and `getIncomeRulesReport(month)` compares expected with ledger (Settings > Income rules > Check a month). Neither counts amounts assigned by hand. The spec's "match by category" is not built: income has no category.
- Months roll over: a category opens a month with last month's available if positive; cash overspending does not carry, it comes out of the next month's Ready to Assign (`rollCategories` in `allocations.ts`).
- Investment accounts are tracking accounts: in net worth and goals, not in the monthly budget.
- A transfer is two transactions sharing `transfer_pair_id`; the amount is mirrored, date and cleared are per leg. Between budget accounts it moves nothing in the budget; across the budget edge the budget leg is spending or income and may carry a category.
- Each on-budget credit card has a payment category (`categories.credit_card_account_id`, id `payment-<accountId>`, in the `credit-card-payments` group). Its activity is derived in `rollCategories`: card purchases add to it, refunds and payments (transfers into the card) draw it down. It is managed by the card: no rename, delete or transaction use. Purchases move in full, even past the spending category's balance; that shortfall is cash overspending and comes out of the next month's Ready to Assign.
- Imported transactions (`imports.ts`) enter the inbox: `approved = 0`, cleared, uncategorized, with `import_id` = `<bank account id>:<bank transaction id>` and a deterministic row id so two devices importing the same fetch write the same rows. They count in balances and Ready to Assign straight away. Before adding one, the importer folds it into an unreconciled manual entry in the same account with the same amount within 3 days (closest date, then payee), which keeps its payee and category and gains `import_id`. `listInbox` offers the same candidates the other way round (`mergeImport`) for entries made after the import. Deleting any transaction that has an `import_id` records it in `dismissed_imports`, so the next fetch skips it. `external_accounts` (id = the bank's account id) maps a bank account to an app account; unmapping sets `account_id` to null rather than deleting, because deletes are permanent.
- Payee rules (`payee-rules.ts`, synced table `payee_rules`): a payee containing the rule's words (whole words, any case, longest match wins) is categorized when imported into an on-budget account, but stays in the inbox for approval. `applyPayeeRules` fills in uncategorized inbox items after a rule is added. Suggestions from the model are hints only: the server keeps answers about categories it offered, and a person presses Use.
- Investment accounts (`investments.ts`, synced tables `investment_accounts`, `account_valuations`): settings are kind (brokerage, IRA, 401(k), 403(b), 457, 401(a), SEP IRA, SIMPLE IRA, 529, other), tax type (roth, traditional, taxable, 529; the kind limits the choice via `taxTypesFor`: brokerage is taxable, 529 is 529, a retirement plan is traditional or Roth, `other` allows any, and changing the kind moves a tax type that no longer fits to the kind's usual one), owner (a member, or null for joint) and mode (units or holdings). The settings row's id is the account's id; an account with no row (older, or made by the YNAB import) reads as taxable, joint, units, and gets its row on the first change. A valuation is a dated market value in cents with a deterministic id (`valuation-<accountId>:<date>`), so one account has one value per day on every device; recording the day again replaces it. `source` is `manual` or `sync`: a bank balance (`recordBankBalances`, called after Check balances or Import transactions in the Connections panel) refreshes an earlier bank value for its day but never overwrites a typed one. The daily server pull does not carry balances yet. Settings are chosen in the Add Account dialog; the gear button in the investment account's toolbar opens a dialog to change them and keep the value history.
- The YNAB import (`ynab-parse.ts`, `ynab.ts`) reads the "Export Budget Data" files, Register.csv and optionally Budget.csv. `planRegister` pairs the two sides of transfers and joins `(Split i/n)` lines; the import is one transaction with deterministic `ynab-` ids and refuses to run twice. Memos are dropped (no memo column). After importing it compares each category's activity and available with Budget.csv and reports differences. The format handling is written from YNAB's documented export, not from a real file, so try a real export first.
- Reconciling locks every cleared transaction in an account and posts an uncategorized cleared adjustment if the bank balance differs; locked transactions can't be edited or deleted.
- The activity feed is derived from the `messages` log, not stored. Messages carry no write id, so `activity.ts` splits a row's messages into actions at a delete, at `created_at` (the last column of every insert) and at a repeated column. Who made a change comes from the `devices` row (synced) that ties a device id to a member.
- Lists must sort deterministically across devices: break ties with `created_at, id`, never `rowid` (rowid is arrival order on one device, so two devices would show the same rows in different order). Transaction splits are the exception until they get a sort column.
- Money is **integer cents** in the database and the client. Never use floats for amounts; rounding remainders fall to Ready to Assign.

**Stack (per spec)**

- Local-first: the whole app is a static bundle with SQLite (WASM) inside it. Domain logic runs in a web worker; the UI talks to it through one typed message API (`connect`/`serve` in `packages/core/src/rpc.ts`). There is no business API.
- Storage: SQLite in OPFS (`opfs-sahpool` VFS) behind the `StorageAdapter` interface. Only one tab can own the database at a time (guarded by a Web Lock). If OPFS is unavailable the worker falls back to memory and the UI warns loudly.
- Schema changes: append-only versioned migrations in `packages/core/src/migrations.ts`. Never edit a released migration; add a new one. The app refuses to open a file from a newer schema.
- Per-device settings (last backup time) live in `localStorage`, outside the budget file, so they never sync.
- Sync (Phase 2, push/pull, full-file setup, the status banner and the server's bank proxy built; server-side import queue not yet): optional. Every write becomes a change message with a hybrid logical clock timestamp; newest-wins per field: a row is rebuilt from the newest message per column, so arrival order never matters, and a delete is permanent. A sync is one `POST /api/sync` (push unsynced, pull after the server cursor); if the Merkle roots still differ, the device diffs the tries and re-exchanges everything from the earliest differing minute. A device that syncs with the server holding no file (or one 1000+ messages behind) uploads its SQLite image with the log position it contains (`PUT /api/sync/file?cursor=`); a new device downloads it (`GET /api/sync/file`), then syncs from that position. A device with its own budget that has never synced is refused (409) if the server already holds one: budgets are never merged, and the UI offers to replace the device's budget with the server's instead. The server keeps its own copy of the trie hashing (`apps/api/src/merkle.ts`) because it cannot import core; both test suites assert the same root hash. The server is a small Node + SQLite service on the same origin as the app (required for passkeys); it relays changes, signs people in and proxies SimpleFIN. `apps/api` is its placeholder.
- Import: SimpleFIN via the server, YNAB history import once. Aggregator tokens live only on the server, never in the client: `POST /api/bank/fetch` returns normalized accounts and transactions (pending ones are held back) and the device inserts them. SimpleFIN allows about 24 requests a day per token and 90 days per request.
- Rules that create rows (income rules, unit purchases) use deterministic IDs so two devices converge on one row.
- Not yet decided: TanStack Query (the worker calls are already async; add it only if caching becomes necessary).

**Testing approach:** credit card and rollover logic is subtle, so build it test-first using real YNAB months as fixtures. Core tests run the real SQLite engine in memory under Node, so SQL is exercised exactly as in the browser. Property tests (fast-check) cover money arithmetic. Browser-only behavior (OPFS persistence, service worker, tab locking, file import/export) is covered by the Playwright suite in `apps/web/e2e`.
